# 给大模型一双手

> 从一个大模型，到一个 Agent

上一篇里提到过：大模型本质上是一个纯粹的、无状态的文本预测器。一段文字送进去，一段文字吐出来。答完了，这次推理在显存里的临时激活值就释放了，模型本身没有任何改变。

这就带来了一个极其现实的物理限制：**它只有嘴，没有手。**

如果你在输入框里对它说：

> 帮我把服务器上超期的临时日志全部删掉，并把磁盘占用率发到告警群里。

它可能会极其礼貌且逼真地回复你：“好的，已为您找到并清理了 14 个日志文件，释放了 2.3 GB 空间，并已将通知推送到群聊。”

但你登录服务器一看，磁盘占用率纹丝不动，群里也一片死寂。

大模型并没有撒谎的恶意，它只是根据语言概率，补全了一段“在人类语境中最像处理成功”的文字。它的大脑被锁在机房的矩阵运算里，它的代码在物理上根本触碰不到你硬盘里的任何一个字节。

要让它从一个“只能动嘴的顾问”，变成一个“能替你办事的 Agent”，我们必须在工程上给它装上一双手。

## 所谓“动手”，其实依然是在发文本

直觉上，很多人会以为“给大模型加工具”是在模型内部焊接了某种底层接口，或者赋予了它操纵操作系统的特殊神力。

根本没有这种东西。在网络通信的物理层面上，大模型与外部世界的交互通道，从始至终只有一条：**结构化的文本数据流**。

让大模型动手的秘密，其实是一场由**宿主程序（Host Runtime）**与模型协同演出的协议对接：

### 1. 递给模型一份“工具说明书”（JSON Schema）

在向大模型发送请求时，宿主程序除了带上用户的提问，还可以在请求体中夹带一个名为 `tools` 的数组。这个数组用标准的 JSON Schema 格式，向模型严谨地描述当前环境支持哪些能力：

```json
[
  {
    "type": "function",
    "function": {
      "name": "delete_files",
      "description": "删除指定路径下的匹配文件",
      "parameters": {
        "type": "object",
        "properties": {
          "directory": { "type": "string", "description": "目标目录" },
          "pattern": { "type": "string", "description": "文件匹配规则，如 *.log" }
        },
        "required": ["directory", "pattern"]
      }
    }
  }
]
```

这份说明书告诉模型两件事：第一，你手头有这么个叫 `delete_files` 的工具；第二，如果你想用它，必须提供哪些具体参数。

### 2. 模型输出结构化的决策数据

当模型读到用户的诉求“删掉临时日志”，又在上下文中看到了这份工具说明时，经过专门指令微调（Function Calling Fine-tuning）的模型就会做出判断：此时不应该直接向用户输出普通聊天文本，而应当调用工具。

于是，模型会停止吐出自然语言，转而生成一段精确符合规范的 JSON 串：

```json
{
  "tool_calls": [
    {
      "id": "call_987654",
      "type": "function",
      "function": {
        "name": "delete_files",
        "arguments": "{\"directory\": \"/var/log/tmp\", \"pattern\": \"*.log\"}"
      }
    }
  ]
}
```

同时，API 返回的数据包里会标明一个特殊的终止状态：`finish_reason: "tool_calls"`。模型在这里戛然而止，它把麦克风交还给了外面的系统。

请注意：**到这一步为止，服务器上的日志依然一个都没少。** 大模型只是在它的输出里表达了它想调用什么。它没有、也无法亲自运行任何代码。

## 宿主环境：真正的执行者与 ReAct 循环

真正干苦力的，是包裹在大模型外面的宿主程序（也就是你本机运行的 Python、Node.js 脚本，或者像 Codex、Cursor 这样的开发环境）。

当宿主程序收到大模型的这一段 JSON 决策后，真正的机械传动才正式开始：

1. **解析与校验**：宿主程序拦截到 `tool_calls`，解析出函数名 `delete_files` 以及参数 `/var/log/tmp` 和 `*.log`；
2. **权限与本地执行**：程序在真实的操作系统中，以系统赋予的权限执行对应的物理操作（比如调用系统的 `rm` 或文件删除 API），并在硬盘上真实地删除了 14 个文件；
3. **包装执行结果**：本地程序拿到真实的执行输出（例如：`{"deleted_count": 14, "freed_bytes": 2469606195}`）；
4. **将结果塞回上下文**：宿主程序将这一段真实的执行结果，组装成一条带有特殊角色标识的消息（`role: "tool"`），追加到整个对话历史的最末端；
5. **再次呼叫大模型**：宿主程序带着这根变得更长的“上下文绳子”，重新向大模型发起下一次请求。

此时，大模型眼前看到的东西变了：
- 它看到了用户最初的指令；
- 它看到了自己刚才做出的调用决策；
- 它更看到了宿主程序刚刚从物理世界带回来的真实结果。

基于这个最新的现场事实，大模型才终于可以敲定自己的自然语言回答：“我已经为您清理了 `/var/log/tmp` 下的 14 个临时日志文件，总计释放了 2.3 GB 空间。”

这就是人工智能领域极其著名的 **ReAct（Reasoning + Acting）闭环**：

```text
[观察当前上下文] 
      ↓
[思考并决定调用工具] 
      ↓ (输出 JSON)
[宿主程序在真实世界执行] 
      ↓ (产生真实数据)
[将执行结果写回上下文] 
      ↓
[再次观察并决定下一步]
```

## 从“一个工具”到“自治 Agent”

如果整个过程只循环一次，大模型充其量只是一个支持自然语言语法的遥控器——你说一句，它调一下，完事。

真正的 **Agent（智能体）**，诞生于**连续自治的多步循环**中。

设想一个复杂任务：“排查为什么本地服务返回 502，并设法恢复它。”

面对这个目标，你并没有、也不可能提前预知每一步该干什么。宿主程序只是给模型提供了一组基础的系统探针工具：`execute_command`（运行 shell 命令）、`read_file`（读文件）、`write_file`（改文件）。

随后，宿主程序的外部代码进入了一个死磕到底的 **While 循环**：

- **第 1 轮迭代**：
  - 模型决定执行：`curl -I http://localhost:3000`
  - 宿主返回真实错误：`Connection refused`
- **第 2 轮迭代**：
  - 模型看到连接被拒，推测进程挂了，决定执行：`ps aux | grep node`
  - 宿主返回：空（没有任何 node 进程）
- **第 3 轮迭代**：
  - 模型确认服务没起，决定查看最新的日志：`tail -n 20 /var/log/app.err`
  - 宿主返回报错堆栈：`Error: Cannot find module 'dotenv/config'`
- **第 4 轮迭代**：
  - 模型根据报错定位出缺少依赖，决定执行修复：`npm install dotenv`
  - 宿主返回安装成功，耗时 3 秒；
- **第 5 轮迭代**：
  - 模型重新尝试拉起服务：`npm run start`
  - 宿主返回：`Server listening on port 3000`
- **第 6 轮迭代**：
  - 模型做最后验收：再次 `curl -I http://localhost:3000`
  - 宿主返回：`HTTP/1.1 200 OK`
- **第 7 轮迭代**：
  - 模型看到 200 OK，判定任务彻底达成。它不再输出任何 `tool_calls`，而是输出最终的文字说明：“排查完毕，502 原因是缺失 dotenv 依赖导致 Node 进程崩溃，已补全依赖并重新拉起服务。”
  - 外部 While 循环检测到模型没有新的工具请求，跳出循环，任务圆满结束。

在整个 7 轮流转中，没有任何一步是人类手工遥控的。模型根据上一轮工具返回的**不可预测的客观现实**，在运行时动态决定下一步该看哪里、该动什么。

**大模型自身从头到尾没有记忆，也没有状态。** 所有的状态推演、因果关系与现场证据，都是被宿主程序通过字符串拼接，不断追加在不断膨胀的上下文窗口里，像滚雪球一样向前滚动的。

所谓的 Agent，本质上不过是：**一个用 JSON 协议与操作系统对话、以大模型为决策中枢、在外部由 While 循环驱动的状态机。**

## 真实世界里的工程硬伤

理解了这套底层机制，你就不会对 Agent 产生任何玄学幻想，更能一眼看穿它为什么在真实场景中频频“翻车”：

1. **死循环死胡同（Infinite Tool Loop）**：
   如果宿主执行某个命令一直报 `Permission denied`，而模型没有从上下文中提取出“缺权限”这个因果，它很可能会在 While 循环里反复修改参数重试几十次，直到把你的 token 或 API 余额彻底烧光。
2. **上下文暴击（Context Bloat）**：
   如果模型随手执行了一个 `cat large_database.dump`，一个 50MB 的文本瞬间塞进 `role: "tool"` 的消息里。上下文窗口瞬间被垃圾数据淹没，不仅极度昂贵，还会直接触发上一篇讲过的注意力退化（Lost in the Middle），导致模型瞬间“变笨”，甚至直接报超限错误崩溃。
3. **幻觉参数（Hallucinated Arguments）**：
   模型完全可能根据虚妄的语料记忆，编造出一个本地根本不存在的文件路径或 API 参数。宿主程序必须做严密的防御性校验，否则不可预期的参数直接丢进底层系统，可能会造成灾难性的破坏。

---

现在，大模型不仅有了眼睛（上下文），还有了双手（工具调用与 ReAct 循环）。

但随着我们交给它的任务越来越重，新的问题接踵而至：我们不可能把成百上千个工具一股脑全堆给它，它也无法仅靠当前会话记住上周讨论过的事情。

这就引出了下一篇的主题：业界那些让人眼花缭乱的热词——Memory、Skill、MCP 与 Subagent，到底是在解决什么工程麻烦？
