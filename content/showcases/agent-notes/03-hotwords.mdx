# Agent 热词都在说什么

> MCP、Memory、Skill 和 Subagent

上一篇我们拆解了 Agent 的底层物理骨架：它本质上是在无状态的大模型外面，套上了一个由 JSON Schema 协议约束、由真实代码执行、依靠上下文累加状态的 While 循环。

如果单看这个定义，Agent 的原理似乎并不复杂。

但只要你稍微关注行业动态，就会被一系列铺天盖地的新名词轰炸：Memory、RAG、Skill、MCP、Subagent、Goal 模式……许多人因此产生了一种认知焦虑，觉得每隔三个月行业就会诞生一种颠覆性的新架构。

事实恰恰相反。

这些概念的爆发，根本不是因为大模型突然掌握了什么未知神通，而是因为那个质朴的 While 循环在进入复杂的工业生产环境时，**狠狠地撞上了三堵物理高墙**：

1. **上下文容量与推理成本的墙（Context Limit）**：你不可能把 100 个工具、500 页操作手册和过去一个月的历史记录，全部一股脑塞进 Prompt 里；
2. **工具接口碎片化的巴别塔（Fragmentation）**：每对接一个新系统（GitHub、Slack、数据库、本地文件），开发者都要重新手写一套 Tool 适配，全行业都在重复造轮子；
3. **单一大脑的认知过载（Cognitive Overload）**：让一个会话既负责规划全局、又负责写业务代码、还负责去翻几千行终端报错，20 轮交互之后，上下文被海量杂音污染，模型开始前言不搭后语。

今天所有的 Agent 热词，本质上都是工程界为了翻越这三堵墙而搭建的特化组件。

把这层窗户纸捅破，把它们放回工程架构图里，每一个词的真身其实都极其清晰。

## 一、Memory（记忆）：从易失工作区到外挂持久化

在第 1 篇里我们讲过，大模型本身没有任何物理存储介质，会话结束显存一清，所有对话烟消云散。

为了让 Agent 在今天知道你昨天干了什么，工程界必须给它外挂**记忆系统（Memory）**。

在实际架构中，记忆严格划分为两个截然不同的层次：

### 1. 短时工作记忆（Working Memory）
就是当前的上下文窗口（Context Window）。它直接参与当前轮次的注意力矩阵计算，精度最高、反应最快。但它的缺点是极度昂贵，且只要会话关闭或窗口被撑爆截断，它就彻底消失。

### 2. 长时外部记忆（Persistent Memory）
保存在硬盘上的物理存储：可以是一个简单的本地 Markdown 文件夹、一个 SQLite 数据库，或者一个向量数据库（Vector DB）。

**长时记忆是如何生效的？**

这里必须记住一个核心定理：**没有被装进当前上下文的内容，对大模型而言在物理上就是不存在的。**

长时记忆要起作用，宿主系统必须在运行时把它“打捞”出来，重新塞进模型的视口中。目前主流有两种工程打捞方式：

- **隐式静默注入（Shadow Injection）**：宿主程序在把你输入的提示词发给模型之前，先在后台拿着你的话去向量库做一次语义比对（Embedding Similarity），捞出最相关的 3 条历史记录，神不知鬼不觉地拼进 System Prompt：“*以下是系统检索到的该用户长期习惯：他习惯使用 TypeScript、不喜欢过多的防御性注释……*”。大模型一睁眼就看到了这些设定，表现得就像它“一直记得你”一样。
- **显式工具检索（Active Tool Retrieval）**：宿主程序赋予模型一组专属工具（例如 `search_memory`、`read_user_profile`）。当模型发现自己缺乏背景时，自己主动发起工具调用，去长时数据库里翻阅资料。

所谓的 Memory，并不是赋予了模型脑细胞，而是**一套在外部自动化进行持久化存储、并在适当时机把有效信息重新灌回上下文的检索管道**。

## 二、Skill（技能）与渐进式披露（Progressive Disclosure）

刚开始构建 Agent 的开发者，最常犯的错误就是“把公司的全部家当一次性全给它”：不仅把 50 个工具的 JSON Schema 全塞进请求，还附带了厚厚几十页的 API 规范和编码守则。

这会立刻引发灾难：
1. **上下文被无效消耗**：真正的任务可能只需要其中 2 个工具，其余 48 个工具的描述白白浪费了宝贵的 token 预算；
2. **工具选择漂移（Tool Drift）**：工具越多，模型在做决策时的注意力越容易涣散，甚至产生幻觉，在不恰当的时机选错工具。

为了解决这个问题，**Skill（技能）**机制应运而生。

Skill 的工程哲学叫作**渐进式披露（Progressive Disclosure）**。它把庞大的能力体系拆成了两层：

- **第一层：常驻的极简元数据（Index Layer）**  
  在模型的系统提示词里，只留一份极度精炼的能力清单（往往只有几十个 token）：
  > - `audio-transcribe`：用于处理音频转录与字幕生成
  > - `k8s-deploy`：用于管理生产集群与发布容器
- **第二层：按需挂载的具体指令与脚本（Payload Layer）**  
  当用户说“帮我把这个视频的声音提取成字幕”时，模型首先命中第一层的目录。此时，Agent 才会动态触发一个内置行为：读取对应的 `audio-transcribe/SKILL.md`，把详尽的 ffmpeg 参数说明、执行脚本甚至专属临时工具，临时注入到当前上下文。

任务完成后，这些临时注入的重型材料立刻从上下文中剥离。

Skill 让 Agent 拥有了“按需翻书”的能力：平日只带目录上班，遇到特定专业问题，才去工具箱里调出专属的说明书与重武器。

## 三、MCP（Model Context Protocol）：AI 时代的通用外设总线

在 2024 年底之前，整个 Agent 生态四分五裂。

假设开发者写好了一个能查询本地 SQLite 数据库的优秀工具：
- 想给 Claude Desktop 用，得写一套 Claude 的插件格式；
- 想给 Cursor 用，得按 Cursor 的 Rules 重新封装一遍；
- 想在自己的 Python 脚本里用，又得写成 LangChain 的 Tool。

每家大模型厂商、每一个开发环境，都在发明自己的工具调用格式。

为了终结这种无休止的内耗，Anthropic 提出了 **MCP（Model Context Protocol，模型上下文协议）**，并在开源社区迅速演化为事实上的行业标准。

**MCP 到底是什么？用一句话说：它是 AI 时代的 USB-C 协议。**

它将体系清晰解耦为两端：
- **MCP Client（客户端/主机）**：拥有大模型决策能力的环境（例如 Cursor、Claude Desktop、你的自研 Agent）；
- **MCP Server（服务端）**：具体提供数据与能力的软件（例如本地文件系统服务、GitHub 服务、PostgreSQL 服务）。

两者之间使用标准通用的 **JSON-RPC 2.0 协议**通信，通常通过本地的标准输入输出流（`stdio`）或远程的 Server-Sent Events（`SSE`）传输数据。

MCP 规范定义了三大标准化核心原语（Primitives）：

```text
       ┌──────────────┐     JSON-RPC 2.0      ┌──────────────┐
       │  MCP Client  │ ────────────────────> │  MCP Server  │
       │ (Cursor/LLM) │ <──────────────────── │ (GitHub/DB)  │
       └──────────────┘                       └──────────────┘
                                                     │
                             ┌───────────────────────┼───────────────────────┐
                             ↓                       ↓                       ↓
                       [Resources]                [Tools]                [Prompts]
                     (只读数据与文件)           (带副作用的操作)         (预设交互模版)
```

1. **Resources（资源）**：向模型提供只读的上下文数据（如日志文件、数据库元数据、代码快照），不触发修改；
2. **Tools（工具）**：具有执行副作用的函数（如发送 Slack 消息、创建分支、写数据库），需要严格的参数传递与权限确认；
3. **Prompts（提示词模版）**：预设的命令流模版（类似快捷斜杠命令 `/review`）。

有了 MCP，开发者只需要为自己的系统编写一个标准的 MCP Server，全世界成百上千种支持 MCP 的 Agent 软件便能立刻即插即用，彻底拉平了工具生态的接入鸿沟。

## 四、Subagent（子智能体）：上下文隔离与并发分工

很多初学者直觉上认为，一个 Agent 既然已经能执行多步循环了，那就让它从头到尾一个人干到底。

但在复杂的真实工程里，这种“大一统 Agent”很快就会崩盘：

假设主任务是“给一个老项目重构认证模块并修复所有测试用例”。
如果主 Agent 自己在同一个上下文里跑测试、看几百行的单元测试报错堆栈、改代码、再跑测试……仅仅过了三轮，原本珍贵的上下文就被大量的报错字符淹没（这被称为**上下文污染，Context Pollution**）。当它回过头来准备进行高层次的模块设计时，它早就被刚刚那些琐碎的细节带偏了。

为了解决这个问题，现代 Agent 体系全面转向了 **Subagent（子智能体）** 架构。

**Subagent 的工程真身，其实就是操作系统里的 `fork` 进程：**

1. **会话环境隔离**：主 Agent 发现某项具体子任务（例如“排查某个特定的网络超时错误”）非常繁琐，它不会亲自在当前会话里做。相反，它作为调度者，调用一个名为 `invoke_subagent` 的工具；
2. **派生纯净上下文**：宿主系统在后台开辟一个**全新的、独立的会话实例**，赋予这个子 Agent 单一的职责和收敛的工具集；
3. **子会话内部闭环**：Subagent 在它自己的上下文里反复执行了 15 轮命令行排查，看了海量的错误日志，把所有杂音全部留在子会话内部；
4. **高纯度结果回传**：排查结束，Subagent 只提炼出一句核心结论：“*原因定位在第 48 行连接超时，建议将 timeout 从 5s 改为 30s*”，作为工具执行结果返回给主 Agent。

主 Agent 的上下文因此从始至终保持着极其干净的全局视角。

在工程上，Subagent 还可以**并发运行**：主 Agent 可以一口气派生三个子 Agent，分别去做竞品调研、代码扫描与文档阅读，最后在主会话中汇总收敛。这就是多智能体协同（Multi-Agent System）最朴素、最有效的本质——**通过上下文物理隔离实现关注点分离（Separation of Concerns）**。

## 拼接全景

回过头看，这些眼花缭乱的名词终于落回了一张严密的架构图里：

- **Memory** 解决了“信息跨越时间持久保留”的问题；
- **Skill** 解决了“海量专业能力如何按需精细加载”的问题；
- **MCP** 解决了“不同工具与客户端如何用一套标准协议互通”的问题；
- **Subagent** 解决了“复杂长任务如何通过上下文隔离进行分工协同”的问题。

它们没有发明任何魔法，而是在一步步为那个最初简陋的 While 循环打上补丁，把它武装成具备工业级可用性的智能系统。

但只要这套系统开始被赋予越来越强的能力、能够调用越来越多的 MCP 工具、派生越来越多的 Subagent，一个最根本、最危险的问题就浮出了水面：

这套系统在你的电脑上，到底有多大权力？如果它失控了，谁能制止它？

这就是札记最后一篇要拆透的问题：权限与安全边界。
