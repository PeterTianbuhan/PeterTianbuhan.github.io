昨天晚上，我梦见一块纯白的巨大屏幕。屏幕中央只有一个提示框，随着我的输入与对话，屏幕空间不断被重塑，各种工作界面随之展开。

醒来之后，我一直在想：为什么今天的 Agent 交互离这块屏幕还差得这么远？

## 聊天流的窒息感

今天的 Agent 几乎全被困在单维度的聊天框（Chat Stream）里。人发一段文字，模型回一段文字；即使模型能吐出图表、网页片段或交互卡片，这些内容最终还是被塞进一条纵向滚动的瀑布流中。

但人类处理复杂问题时的认知方式从来不是单向串行的。

思考和创作需要空间。当我们在构思一个系统或打磨一篇文章时，我们需要左边留着大纲，中间铺开展开的草稿，右边随时调出参考资料，并在发现冲突时拉出一个并排差异视图。在传统的聊天流中，这一切都被降维成了一根细绳——内容一旦滚出视口，就退出了即时工作记忆；前后的上下文一旦变长，交互便彻底失去了位置感。

走出聊天框，需要的不是在对话气泡旁边加几个辅助侧边栏，而是重新审视软件本身的组织方式。

## 软件的本质构成：数据、能力与界面

从工程底层来看，所有交互式软件都可以拆解为三个正交的维度：

1. **数据与状态（Resource）**：系统中存在或流动的实体。一份代码文件、一篇文章草稿、一条日程、数据库中的订单记录，或是内存中正在变化的执行上下文。
2. **能力与操作（Capability）**：对状态施加改变的方法。检索、排序、持久化、调用 API、发送网络请求、编译或撤销。
3. **交互与呈现（Interface）**：让人感知数据并触发能力的视听载体。代码编辑器、时间轴、甘特图、差异对比器、播放控件或语音提示。

在纯粹的计算模型中，这三者本没有天然绑定的理由。同一份数据完全可以用不同的界面呈现（一组表格数据既可以展示为网格，也可以投影为散点图）；同一种能力也可以从不同的界面被调用。

但在我们今天所熟悉的计算机世界里，这三者被焊死在了一起。

## App 是编译期的预先绑定

所谓的“App”，本质上是开发者在编译期把特定的 Resource、Capability 和 Interface 强行打包后的封闭交付物。

Spotify 将音频流数据、推荐算法与一套固定的播放界面打包成一个二进制包；系统日历将事件存储、提醒调度与月视图界面打包成另一个二进制包。

这种打包在历史上是极其合理的，甚至是唯一的工程解法。过去的计算机没有任何语义理解能力，程序无法获知使用者眼下的真实目的。开发者必须预先假设用户的所有行为路径，把所有页面、菜单、跳转关系与数据绑定在代码中全部硬编码下来。

用户使用软件的过程，本质上是在别人提前修筑好的水泥迷宫里，寻找一条与自己目标最接近的通路。

真实的任务从来不按照 App 的边界发生。以“准备一场期末考试”为例：它需要教材资料（PDF 阅读器）、错题与反思（Markdown 笔记）、考试日程（日历）以及自测测验（在线题库）。今天的使用者必须肉身充当数据总线，在五六个 App 窗口之间来回切换、复制粘贴。App 的边界不但保护了各自的数据孤岛，也割裂了任务的完整上下文。

## 动态场景（Scene）：运行时的视图树合成

Agent 的核心价值，在于它第一次为计算系统提供了两项关键能力：**动态理解模糊意图**，以及**跨领域调度底层 API**。

这两项能力一旦成立，“编译期强行绑定”的前提就不复存在了。

我们不再需要预先存在的庞大单体应用。取而代之的，是一个开放的运行时空间——我称之为 **Scene（场景）**。

Scene 不是另一个超级 App，而是一个具备动态布局与状态编排能力的白板运行时：

- 当我说“整理刚才讨论中的几点冲突”，Scene 会在当前视口中挂载一个并排的差异对比组件（Interface）；
- 当我说“这段逻辑我需要手动细化”，一个极简的编辑器组件才会在对应文本旁边就地渲染；
- 当我需要核对某些外部依据时，检索组件直接在当前工作的边缘展开，消费底层的检索能力（Capability），呈现相关数据（Resource），随后可以被随时折叠或挥去。

这里的界面组件（Interface）不再是某个私有软件的禁脔。只要底层的数据协议与操作能力兼容，一套通用的时间轴、代码对比器或列表视图，就可以在任何场景中被按需挂载。

任务结束之后，核心数据（Resource）沉淀回它该去的持久化存储，而临时的界面组件自然解散；或者，整个 Scene 的排布状态被完整快照，等待下次继续推进。

## 个性化的实质：交互习惯与自主边界

固定界面的软件逼迫所有人适应同一套交互路径。而在动态 Scene 中，界面最终会长成每个人自己的形状。

这绝不是换个皮肤主题或改改字体大小那么表面。真正的个性化，是个人心智模型在系统中的投影：

- **信息密度的偏好**：有人在审查代码时习惯先看高层抽象与调用拓扑，有人习惯直接看逐行 Diff；有人需要并排对比，有人需要单列聚焦。
- **与 Agent 的相处边界**：在哪些操作上，系统应当保持静默、先行执行；在哪些具有破坏性或关键转折的节点上，必须打断并等待人工确认。
- **认知节奏的差异**：写作时，系统应当少说话、只默默准备相关资料；而在发散风暴时，系统应当主动抛出反例与边界质询。

这些偏好很难写成一张拥有上百个复选框的设置面板。它是在长期的真实协作中沉淀下来的：每一次人类对界面组件的拖拽调整、对 Agent 决策的撤销或纠正，都在为这个系统提供微调信号。

最终保留下来的，是一套关于“如何组织界面与何时介入操作”的个性化运行时策略。

## 工程基底：双重工具集与 Web 运行时

让这一构想落地的关键，不在于追求一个万能的端到端生成式模型，而在于工程架构上的分层解耦。

在运行时中，Agent 的工具集应当明确分为两类：

1. **领域工具（Domain Tools）**：即现有的 Tool Calling 与 MCP 能力。负责深入具体业务，读取或修改 Resource，执行 Capability（如读写文件、查询向量库、发送请求）。
2. **场景工具（Scene Tools）**：专门操纵视图层与交互树的系统级能力。包括在画布上挂载特定的 Interface 实例、调整组件的视口坐标与尺寸、将组件绑定到特定的数据管道，以及监听组件产生的用户事件。

这种划分在工程上极其关键：**Scene Tools 不会穿透安全边界**。它只负责视图的排布与状态投影，无法越过权限直接碰触敏感数据。安全性依然被严格锚定在领域工具的授权模型中。

而实现这一构想的最现实底座，就是现有的 Web 体系。Web 生态已经拥有世界上最丰富、最成熟的解耦 UI 组件库（从 DOM、Web Components 到各类标准图形渲染基座）。我们欠缺的并不是界面控件，而是缺少一个能够根据当下意图、在运行时动态编排这些控件的调度中枢。

## 结语

单行文本框与聊天气泡，是我们学会与大型语言模型相处的第一站，但它绝不该是软件交互的终点。

我们想要的，绝不是 Agent 变得更加熟练地扮演一个虚拟的“打工人”，在那些旧时代的固定 App 里替人类笨拙地点击按钮。

我们真正期待的，是软件本身卸下编译期铸造的刚性外壳，化作随人的意图自由流动的容器；在一次次的交互与重塑中，最终严丝合缝地贴合每个使用者独特的思维轮廓。
