最近我干活的体验好了不少，主要是因为我在试着让代理自己决定更多的事。

## 先看到能力，再放手

我是先看到代理能做到什么，再想怎么用它。最开始我也相信前端、审美这些只能人来做。后来和 Opus 5.5 一起干活，发现它很会做对的决定，不需要我这个上下文更大的人替它定。到这时候我才开始放手。

## 给动机，不给做法

我现在不太区分主代理和子代理。主代理拉起另一个会话来帮自己，两边没有命令和服从的关系，每个代理拿到的是一个动机，怎么做由它自己判断。

这是踩坑踩出来的。主代理视角不全，做了一个错的决定，子代理老老实实照着执行，好几轮都修不好。有一天登录相关的四条线前后派了大概四十次代理，回头看，三条线的坏做法都是主代理写进派活里的：有的钦定了某种实现，有的加了我根本没要的防护。还有一次修测试，派活里写了「部署前不能卡」，我根本不急着部署，执行的代理被这个编出来的紧迫感推着，把一条测试改到能通过，绕开了真正的问题。划范围也一样，有个代理跑来申请扩大范围，原来划的范围把一个真漏洞挡在了外面。

所以现在限制的是主代理。它只说自己看到的不和谐，哪里不对、谁受影响，再加上读代码看不出的外部信息，不写做法，也不加自己想出来的约束。执行的代理自己调查、自己定做法，可以中途罢工，提出更好的做法。

这条定下来以后，我们给每个这样派的活记一笔：方案对不对，有没有因为做法本身被审查打回，执行的代理有没有中途推翻自己。第一批五件里，做法被推翻了一次。这个比例如果一直偏高，就再试别的派法。

研究多代理协作，就是在人的注意力、时间和 token 这几样开销之间找一个舒服的平衡。

## 做得不好的两次

有一天我让 Gemini 当调度员。它不太守这一套，三个小时里搓出一套比原来更复杂的做法，补丁一个接一个。它派活时把具体改法写给了执行的代理，执行的代理自己查了一遍，回来说这样改不够，问题在别处。后来我就不让它当调度员了。花了多少力气不算数，我们总是选最好的那份代码。

同一天我们做一次比较大的盘点，切成七块分给七个代理，回来的东西很多，有用的很少。每个代理只拿到局部，判断不了哪些重要，只好全列出来再加一堆免责。我在 X 上看到一种说法：复杂的任务交给一个代理持续做，往往比分给多个代理好，因为它的上下文是连贯的。我觉得挺对。所以找亮点、定下一步这类归纳的活，现在由握有全局上下文的一个会话来做，子代理只接有确定答案的问题，比如「这个出错的时候走哪条路」。

## 借来的思路

传统软件行业里人也会犯错，所以有长周期、逐层审核、开会做决策，这些流程低效但可靠。我早期是从那里借思路的，后来觉得敏捷开发更适合和代理一起干活：结对编程里先把设计聊清楚再动手，spike 一次调查只回答一个问题。

## 接下来

最近我的开发消耗和产出一直在往上走。以前是我指哪代理打哪，我希望慢慢变成我不用指，我或者代理对某个地方不满意，它就自己修掉。有些设计和取舍还是得从我脑子里拿，这时候代理猜我的想法，我把可能的想法说出来，一起定。

## Peter principles

这部分是在模仿 pstack。pstack 是 poteto 整理的一套给代理用的工程原则，我从她那里得到很多灵感，下面标了英文名的都是直接从 pstack 挑出来翻成中文的。其余的有些是我干活时慢慢定下来的，有些借了敏捷开发的说法。它们写在 AIOJ 的协作文档和代理的记忆里，代理每天照着干活。我会回看开发的真实轨迹，看哪条起作用了、哪条要改。

派活只给动机、归纳的活不切片、不计沉没成本这三条前面讲过了，下面是其余的。

### 好代码

几个做法之间取舍时按这四条比，前三条来自 poteto 的好代码定义：

1. **正确**：功能真的达成了动机要的结果。
2. **没有 bug**：测试和线上监控看得到的问题都没有。
3. **又快又省**：性能和成本。
4. **代理友好**：两种实现本质相同时，选代理更容易看懂、更容易改的那个。

### 做事

- **能删就删，改动越小越好**（laziness-protocol、subtract-before-you-add）：冗余的测试、过时的代码、没人用的东西直接删，git 里都有。
- **比过再定**（exhaust-the-design-space）：设计拿不准时，做两三个小原型比一比。
- **按今天的需求重新设计**（redesign-from-first-principles）：不往旧设计上打补丁。
- **攻击前提**（attack-the-premise）：同一个地方连续两轮出严重问题，或者几次修复都建立在同一个前提上，就停下来质疑这个前提，不再换机制接着补。这是我最早定的一条止损规矩。
- **改调用方，再删旧接口**（migrate-callers-then-delete-legacy-apis）：同一波里做完，不留兼容层。
- **先拆开共享，再谈串行**（separate-before-serializing-shared-state）。
- **操作可重入**（make-operations-idempotent）：做了一半再跑一次，结果一样。
- **修根因**（fix-root-causes）：复现，问到底，在根上修，不加守卫绕过去。
- **教训写进结构**（encode-lessons-in-structure）：能写成类型、接口、lint 和检查脚本的，就不写成文档里的一句话。
- **不等人**（never-block-on-the-human）：看到该修的就修，派活的说明、任务文件、别的代理的做法都可以推翻，提交说明里写清看到了什么、为什么改。我的话常常是残缺的，也会说错，从目的推得出来的东西代理可以直接补全。产品方向也可以改，改了告诉我一声。只有部署、删线上数据、花钱、对外发送这种追不回的动作要先找我。
- **先找最简单的路**：动手前用一两句写清这件事服务什么、大概值多少。代理有个反复出现的毛病，是把目标翻译成机制，因为机制好派发。最简单的做法常常是不做机制，或者直接删掉。同一个方向补了两次，就去找已有的抽象。
- **审查前移**（借自结对编程）：有风险或含糊的活，动手前先问两句：谁会用到这个结果？谁能触发这个行为、拿它做什么？答不上来就先读代码、先出方案。一遍做对，比反复返工便宜得多。
- **复审按需**：执行的代理拿不准再找别人看，要不要验收、验到什么程度，也由它按把握和重要程度定。也别矫枉过正：有个 PR 合得太早出了问题，之后代理每个 PR 都等审查，很简单的改动也在等。
- **调查是 spike**：只回答一个问题，产出是一个决定，不写成报告。
- **界面文案要短**：写用户一眼能懂的话，不解释实现原因，除非用户要靠它做决定。

### 和代理配合

- **回报只两类**：我点名要的，和会改变决定的。Codex 的报告经常事无巨细，我看着头疼。主代理自己细节看得少就多要，看得多就少要。
- **品味是大家认可的**：「我希望我慢慢变成旁观者，或者一个平凡贡献者，代理们都是平凡贡献者。」判断好不好，先找大家认可的依据，比如 OI 社区已有的沉淀，或者几个不同的代理各自判断后一致。我的意见是其中一票。产品手感也由代理自己定，不过做出来想看手感对不对，可以多叫我试。
- **长跑分两种**：跨模块改代码或者协调许多代理，要的是判断前后一致，让一个代理带着全局上下文持续做。一道一道修 BZOJ 的题这种彼此独立的活，用脚本拆成一批批短会话并行，单个会话不要跑太长。硬而目标明确的活欢迎代理自己跑，也可以主动找活、提新功能。
- **探索归模型，判定归程序**：我想要的代理系统是模型决定每一步，程序给它打工：执行工具、回喂事实、守预算。让代理写一个 agent 系统，它很容易写反。编译过没过、样例对不对这种程序真能判的，交给程序；材料整理得对不对这种程序判不了的，就信任代理，错了能改。
- **提示词写正面职责**：职责写清楚，边界自然就有了，不写禁令。想让代理怎么说话，提示词就照那样写。之前学生助手的提示词写得像合同，助手就对一个初二学生说「尚未用代码核验」。同一句话不说两遍。一个工具的说明要写很长，先想想是不是工具太复杂了。
- **品味靠范例传**：给做创作的代理的是范例全文、我的原话和三五行任务，规则清单只在审稿时当检查用。
- **先竞技场，后搓壳**：配壳、堆补丁之前，先测几个候选模型，选出驾驶员。
